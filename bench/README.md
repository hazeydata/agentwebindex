## Bright Data Web Unlocker (scrape, paid spend guard)
`collectors/benchmark.py` `_brightdata_scrape` POSTs `{"zone", "url", "format": "raw"}` to `https://api.brightdata.com/request` with `Authorization: Bearer $BRIGHTDATA_API_KEY`; the zone comes from env `BRIGHTDATA_ZONE` (`awi_unlocker`). With no key the provider is `skipped_no_key`; with no zone each call is an error billed 0 and no request is made.
Side Hustle CEO, Fred-approved hard cap **$5/month** (config `spend_budget.brightdata`). Before each request the runner reads the month-to-date estimate from `bench/spend/brightdata-YYYY-MM.json` (month of the request's UTC timestamp, so a new month starts a new file) at $1.50 per 1,000 requests ($0.0015 each). If the estimate is already at $4.00, or the next request would take it past $4.00, the provider stops as `stale_budget` (this `stale_budget` applies only to the Bright Data spend guard; HTTP 402/429 stops use the global `stopped_*` names as for every provider; not published, previous row kept, same path as the other stale reasons). The guard allows at most 2,666 requests a month (2,666 x $0.0015 = $3.999), leaving $1.00 of headroom under the cap. Each request's check, bill and spend-file write run under an exclusive `fcntl.flock` (on `bench/spend/.brightdata.lock`, one lock per provider across months, written atomically via rename), so overlapping runs can't push past the $4.00 stop. Rule 6 (CEO ruling 2026-10-19, RULINGS.md): a missing spend file for the current month fails closed (`stale_budget`, no calls) unless it may be seeded at $0. Seeding is allowed only (a) on the first-ever month, when no `brightdata-YYYY-MM.json` exists at all, or (b) when the previous month's file exists, is valid and is not yet closed. Seeding closes it: under the provider lock (`bench/spend/.brightdata.lock`) the runner first writes `rolled_over_to: M` into month M-1's file (atomic temp + rename), then writes the $0 file for M. Refused: M-1 already says `rolled_over_to: M` (this month's file was deleted; every later attempt refuses too), M-1 rolled over to another month, M-1 is corrupt, M-1 is absent while other spend files exist (gap or deletion), or a later month's file exists. A crash after the marker is written but before M's file exists cannot be told apart from "M was deleted mid-month", so it stays refused: M refuses, and M+1 also refuses (previous month absent). Every spend file (current or previous month) must pass the same validation: `provider` = `brightdata`, `month` = its file month, `requests` a non-negative int, `est_usd` a finite non-negative number (no booleans), and an optional `rolled_over_to` that is a later `YYYY-MM` string; anything else fails closed. Manual recovery for a refused month M (crash after the marker, or a deleted file): (1) make sure no benchmark run is in progress; (2) find the true request count N billed for M, from the Bright Data dashboard (zone `awi_unlocker`, month M) or, if the file was never billed (crash right after the marker), N = 0; sum `billed_units` of `bench/runs/YYYY-MM-*/brightdata/*.jsonl` lines for month M as a cross-check and take the larger; (3) write `bench/spend/brightdata-M.json` as `{"provider": "brightdata", "month": "M", "usd_per_1k": 1.5, "requests": N, "est_usd": N x 0.0015 rounded to 6 decimals}`, with no `rolled_over_to`, and leave M-1's `rolled_over_to: M` marker as it is; (4) commit it. The next run in M continues from N. The M+1 gap lockout clears with the same step: once M's file exists without a marker, the first run in M+1 marks M `rolled_over_to: M+1` and seeds M+1 at $0. If M+1 has already started and its own file was billed, recreate M (step 3), then recreate M+1 the same way with its true count, and add `"rolled_over_to": "M+1"` to M's file. Deleting every spend file looks like a first-ever month and cannot be detected locally. Fail-closed cases: if `bench/spend/` is missing or unreadable, or the spend file is empty, corrupt, for another month or has bad fields, Bright Data alone stops as `stale_budget` with the reason logged ("...; failing closed") and the other providers keep running. The month is taken from each request's UTC timestamp, not the run date (Oct 31 21:30 ET bills to 2026-11). Billing follows the status-line rule: a request bills once a status line arrives (including 403, 429, 5xx); 0 for no response or HTTP 401 (ASSUMPTION, accepted by the CEO). Tests are mocked only and refuse to write mock spend into `bench/spend`.

## Apify (search: RAG Web Browser; browser: Web Fetch)
Both categories bill the same Apify Free-plan pool (`apify_usd_cents`, US cents of the $5 monthly credit), so the meter guard (`meter_budget.apify`, $4.00 stop) runs before every call of either.
- **Monthly cap (Fred, Oct 26 2026 8:25 AM ET, relayed by chief: "Approve $4 Apify cap per month.").** The $4.00 stop is month-to-date for the calendar month, summed across every run of that month, and it is not a per-run limit. The guard takes max(live Apify meter `monthlyUsageUsd`, ledger `data/spend/YYYY-MM-quota.json`). The ledger is keyed by month and starts again at zero on the 1st; a ledger file whose `month` is not the run's month is reset. Spend beyond the cap needs Fred's OK first. Note: Apify's own meter follows Apify's usage cycle, which may not start on the 1st, so early in a month the meter can still carry the previous cycle and block conservatively.
- **Publishing the AWI-RUN-2026-10-26 retest (Fred, Oct 26 2026 8:26 AM ET, relayed by chief via the Side Hustle CEO: "I say yes - why not?").** The retest goes out through the normal `--rebuild-only` path. `bench/runs/2026-10-26/_run-offset0.json` combines the two Apify run summaries (`apify-run-001/run-rag-summary.json` for search, `run-webfetch-summary.json` for browser). `tables.build` reads the logs `bench/runs/2026-10-26/apify/news_2026-44.jsonl` and `newsfetch_2026-44.jsonl`, and each row gets a `run_note` from config `run_notes.apify.2026-10-26` that labels it a preliminary retest: 240 s timeout for rag-web-browser, first apify/web-fetch run, one run, n=21. Measured: search 16/21 pass, median 26.6 s, no timeouts; Web Fetch 19/21 pass, median 2.0 s. The wording claims nothing beyond those numbers.
- **search** `_apify_search`: Store Actor `apify/rag-web-browser` (Standby, `https://rag-web-browser.apify.actor/search`), maxResults 10, settings from the named config `apify_search_config`. The default is `rag-raw-http-t240` (Actor `requestTimeoutSecs` 240; the client waits 240 + 60 = 300 s). It is the longer-timeout retest of AWI-RUN-2026-10-26; `rag-raw-http-t60` and `rag-raw-http-t120` stay selectable. Each log line records the config name.
- **browser** `_apify_web_fetch`: Store Actor `apify/web-fetch` (Standby, `POST https://web-fetch.apify.actor/` with `{"url", "formats": ["text"]}` and a Bearer header). It runs the `newsfetch_*` set, the same frozen article URLs Browserless fetches. `dom_text` is the Actor's `text` and `final_url` is `fetch.loadedUrl`. A body with an error `code` or no `text` raises `HTTP <status>: web-fetch returned no text (<code>)`, and the client times out after 150 s (the Actor's own limit is 2 min). Each successful call bills 0.155 cents: the FREE-tier fetch event at $0.0015 plus Actor Start at $0.00005, from the Actor's public pricing record read 2026-10-26. A call that errors bills the 0.155 guard estimate, which overstates it, because Apify charges no fetch event for a failed fetch.

## Stop rules (config `stop_on_http`)
A provider stops at its first HTTP 401/403 (`stale_auth_error`) and at its first HTTP 402 or Apify payment/usage-limit error code in the body, even with HTTP 200: `payment-required`, `usage-limit-exceeded`, `platform-feature-disabled`, `not-enough-usage-to-run-paid-actor` (`stopped_paid_usage`, from `stop_on_http["402"]`). Each of these stops every category of that provider for the rest of the run (for Apify, search and browser alike), and the categories that did not run show `provider stopped earlier this run`. The other providers keep running. These HTTP stops (`stop_on_http`) apply to all providers, Apify, Bright Data and the rest alike. A provider also stops after `stop_on_http["429_consecutive"]` (3) HTTP 429 answers in a row (`stopped_rate_limited`). After each 429 the runner waits the `Retry-After` seconds the provider sent, capped at `retry_after_max_s` (60 s), and waits `retry_after_default_s` (0 s) when the header is absent. A success resets the streak; a client timeout neither resets nor advances it. Calls are sequential, so a run's concurrency is 1. CEO rule 3 (more than 20% of calls answered 429) still applies to runs that finish. `stopped_*` and `stale_*` runs are never published.

Spend guard (Apify, `meter_budget.apify`): before each call the guard refuses the call (`stopped_budget`, as for an unreadable meter) if max(live meter, ledger) is already at the $4.00 stop or if it plus the next call's estimate would pass $4.00. The estimates are 4.08 cents for a RAG search (`pricing.yaml` `credits_per_call.search`, measured: the live meter moved $0.8563 over the 21 RAG calls of 2026-10-26) and 0.155 cents for a Web Fetch call. A per-call cost the pricing does not define fails closed (`stopped_budget`, "unknown per-call cost"), never assumed to be 1. Worked example at the meter reading of $3.9026: two more RAG searches are allowed ($3.9434, then $3.9842), the third ($4.0250) is refused, and Web Fetch calls (0.155 cents) are still allowed until the next one would pass $4.00. When a call bills more than its estimate, or the month-to-date total passes the stop, the run records `cap_overrun` on the log line, in the run summary and in `bench/spend/apify-cap-overrun-YYYY-MM.json`, with `alert: chief` (the runner does not message anyone; the operator alerts chief). The ledger, meter log and run summary are written atomically (temp file + `os.replace`). Every log line carries `cost_estimate_units`, `cumulative_spend` (month-to-date units after the call) and, for Apify, `cumulative_usd`. Every run summary carries `run_spend_units`, `cumulative_spend_units` and, for Apify, `run_spend_usd` / `cumulative_spend_usd`.

Timeouts (Apify): a client timeout on an Apify call is a fail (`status: fail`, `pass: false`, `timeout: true`, reason contains `TimeoutError`). It is billed at the call's estimate and logged; even a run where every call timed out writes its lines. Other providers keep the CEO status-line rule (no status line = `unbilled_no_response`).

## Adapter contract (collectors/benchmark.py `ADAPTERS`)
`fn(key, item) -> dict`, plus optional `billed_units` (the provider's billing unit; browser = raw minutes), `proxy_gb` and `http_status`.
- search: `{"results": [{"url","title","snippet","published_at"?}, ...]}`
- scrape: `{"text", "html"?}`
- browser: `{"final_url"?, "extracted_value"?, "dom_text"?, "file_bytes"?}`

Marker `selector_text` value format: `"<selector>::<text>"`, with selector = `tag`, `#id`, `.class` or `tag.class`.

**Stale and stopped runs still write their run log.** A `stale_<reason>` or `stopped_<reason>` run's lines go to `bench/runs/YYYY-MM-DD/<provider>/<set>.jsonl` stamped `run_status: stale_<reason>` / `stopped_<reason>` (spend audit); `tables.collect` never publishes a stamped or incomplete log. Only a provider with no data call and nothing billed writes no lines.
